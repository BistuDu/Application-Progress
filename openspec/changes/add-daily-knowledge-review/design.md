# Design

## Context

动机与用户选择见 proposal.md。现有项目详情的 `.pane-body` 独立滚动，“新增问答”位于简介／职责之后；八股题库使用分类、题目列表、单题详情三栏。`questionViewHTML` 同时用于两库，目前直接渲染全部答案；`.q-t` 为 13.5px，而答案内 Markdown h1 可到 19px。不能只放大普通正文而忽略答案标题。

知识库使用 `knowledgeLibrary` v1 单容器，background 的 `withKnowledgeWrite` 串行处理 `KNOWLEDGE_APPLY`，实体 revision 保护编辑。完整 JSON 备份 v1 按字段白名单导出，恢复目前会在队列外读取 current／检查 revision，再进入写队列；新增复习写入后须将最终版本检查移入同一写入事务，避免恢复覆盖并发进度。测试已有 Node chrome 替身和隔离 Chromium/CDP 模型 mock，可复用。

主规格尚为空，两库契约存在于已实现但未归档的变更。本次只创建增量能力，不自动同步或归档前一变更。

## Goals / Non-Goals

**Goals:**
- 在既有 DOM／原生模块架构中，让新增入口与阅读折叠不受长内容影响。
- 将选题、日期、间隔与打卡计算写成可注入时钟和随机源的纯逻辑；所有持久改变由 background 串行提交。
- 复习记录与知识正文整体备份／恢复，保持迁移原子性和并发可解释性。

**Non-Goals:**
- 不增加 AI 出题／判分、云同步、通知提醒、补签、积分或项目题复习。
- 临时作答不进入 local、session、日志、备份或模型请求；不新增答案版本。
- 不改变原导入核对、项目 AI 参考、岗位管理与胶囊行为。

## Decisions

### 1. 固定入口与有状态的阅读折叠

右下角使用一个固定“＋新建问答”，项目视图绑定所选项目，八股视图绑定八股题库。未选项目时禁用并说明“先选择或新建项目”；每日复习子视图和模态核对／编辑面板打开时隐藏，以免遮挡答题和确认按钮。内容区预留底部空间，窄视口不覆盖最后一条操作；复用原添加入口，不将顶部“新建项目”错误重定向到问答。

共用题目展示组件使用可键盘操作的标题切换区、`aria-expanded` 和答案容器；题目建议 20px／强调色，正文 14px，答案内部标题限定至 18px 以下，Markdown 原文不变。编辑、删除、AI 参考生成等操作独立于切换区，答案折叠后仍可访问。展开状态保存在页面内按题 ID 的 Set；新进入库／项目默认折叠，同一上下文重渲染保留状态。“全部展开／折叠”只影响当前筛选范围；八股单题详情也提供同样入口，作用于该筛选集合、切题时继承对应状态。

替代方案：只做 sticky 顶部栏无法满足用户指定的右下角入口；把问答改为新的卡片列表会扩大现有三栏布局改造。采用原布局上的增量变更。

### 2. 单容器 v2 保存学习状态

新增纯模块 `src/lib/knowledge-review.js` 与页面模块 `src/knowledge/review.js`。继续使用 `knowledgeLibrary`，升级 schemaVersion 至 2，新增白名单字段：

```text
review: {
  settings: { dailyLimit: 10, categoryId: '', tags: [] },
  progress: [{ questionId, stage, lastResult, lastReviewedDay, dueDay }],
  days: [{ day: 'YYYY-MM-DD', timeZone, revision, settingsSnapshot,
    createdAt, completedAt,
    items: [{ questionId, questionTitle, questionUpdatedAt,
      status: 'pending'|'remembered'|'needs-review'|'unavailable', ratedAt }] }]
}
```

全局知识容器 revision 继续增加；题目实体 revision 仅由内容编辑增加，不能因打卡导致问答编辑冲突。每日计划独立 revision，提交需携带日期、计划 revision、题 ID；已评分题重复提交返回现有结果，不重复推进间隔或增加打卡。页面仅收到必要状态；不将临时输入发给 background。页面刷新从当前首个 pending 题继续，之前已揭晓但未评分的题重新隐藏答案。

替代方案：独立 storage key 简化知识库升级，但会使完整恢复与题目删除的跨容器一致性复杂化；本次选择单容器一次 set 原子提交。v1 读取时纯归一化补空 review，不在只读时写库，第一次成功变更再保存 v2；失败不覆盖原数据。未知未来版本明确拒绝，禁止当作空库写回。

### 3. 本地日期、稳定每日计划与间隔

日期按当前设备本地日历，不能通过 UTC ISO 截断取日。日运算用日历日期加天，避免 DST 下用固定 24 小时导致偏移。计划记录创建时的时区供追溯；设备时区变化后，以当前本地日期选择已有或新计划，不重写历史日期。刷新、返回页面、从后台激活以及每次提交时检查换日；旧日期提交被拒绝并转到今日，临时回答清空。

数量范围暂定 1–100 的整数，默认 10；分类使用一个分类或全部，多个标签沿用现有“全部标签同时匹配”的语义。可参与题为仍存在且答案非空的八股题；空答案显示跳过原因，不参与虚假自评。候选内先取到期“需复习”（到期日期、上次复习时间排序），再取其他到期题，同优先级可随机；剩余从未选中的候选随机补齐，包括未学题和未到期题。计划最多 min(目标数量,候选数量)，题 ID 唯一；可因随机补题提前复习，按本次结果正常更新间隔。

当天首次“开始”在写队列内生成并固定计划，多页面不能各生成一套。题量／分类／标签调整保存为下一次新计划设置；当天计划生成后锁定并显示“明日生效”，不允许反复换题规避完成条件。初次生成之前可自由调整。

建议间隔参数为 [1,3,7,14,30] 日。首次“记住了”安排 +1 日，之后连续记住依次 +3／+7／+14／+30，达到末级后继续 +30。“需复习”将 stage 重置到起点并安排次日；间隔从实际评分日计算，不从旧到期日追赶。当日不能对同题重复推进，重新浏览已完成题只读，不修改结果。

替代方案：纯随机无法实现薄弱题优先和间隔；引入复杂记忆算法增加不可解释参数。先采用固定、可测试的阶梯规则，后续如需修改再单独提案。

### 4. 复习交互、题目变更与历史

“每日复习”位于八股文题库内部子导航，保留普通浏览入口。单题卡默认只显示题目、序号、可选临时输入框和“揭晓答案”。揭晓后安全渲染已有 Markdown，出现两种自评按钮；保存成功才进入下一题、更新计数。保存失败保留当前页面、揭晓状态和临时输入供重试，离开当前题或刷新后清空临时回答。

计划只记录题 ID、当时题目标题、更新时间与自评，不存答案副本。评分前若内容版本变化，刷新题答并要求重新揭晓再评分；不把旧答案的自评套给新内容。编辑题目不追溯改变已保存历史或自动重置间隔。删除题或答案清空使未评分条目标记 unavailable，说明原因并从当天有效目标中排除；已评分条目和历史保留，题目删除后标注不可用。生成后新增或改分类／标签不改变已固定计划，影响后续计划。若全部条目都不可用且没有已评分题，当天不打卡。

完成条件为有效条目数 >0 且全部已评分；“需复习”也是有效学习完成，显示实际分母及不可用题数。完成时间第一次写入后不撤销。跨日未完成计划保留已评分及 pending 信息，历史中显示未完成，不可补签，新一天依据进度重新安排。

月历以完成日期点亮，可切换月份、点击查看当日题目／自评；未完成日期显示进度而非打卡。当前连续天数截至今天（今天未完成则截至昨天），按相邻日历日期计算；没有补签、零题完成、重复提交增加天数的路径。

### 5. 备份与恢复兼容

`knowledge-export.js` 的完整备份升为 v2，显式挑选 review 字段，保留计划、日历历史、进度和设置，不包含答案副本／临时作答。导入 v1 时初始化为空学习记录；替换确认明确提示当前学习记录会被清空。v2 恢复预览额外展示历史天数、已打卡天数和进度数量，严格验证版本、日期、计划唯一性、状态／阶段与活动引用。历史允许已删除题目的 ID／标题快照；缺失题不恢复为新题，活动计划转不可用。

最终 baseRevision 检查、替换 revision 分配、保存全部在同一知识写队列内，防止预览后发生学习提交被悄悄覆盖。失败、冲突或取消不修改任何部分。恢复时重分配版本，使打开中的旧计划提交必须重新加载。Markdown 仍只导出问答正文，折叠状态和学习记录不混入原导入格式。

## Risks / Trade-offs

- [随机补充可能提前抽到未到期题] → 界面说明“到期优先、不足随机补充”，重复 ID 禁止；测试注入随机源验证优先级与数量而非固定随机序列。
- [本地时间或时区被手工修改] → 保留创建时区和日期，提交时校验当前日期，不提供防作弊或跨设备连续天数承诺。
- [历史累积占用本地存储] → 只存标题与结果元数据，不存答案副本；不自动删除用户历史，存储失败明确展示并保留可重试界面。
- [全文重渲染丢失展开或临时输入] → 折叠 Set 与临时草稿分离，切题／离开才主动清理；通过真实长答案、跨标签与刷新用例验收。
- [前一变更未归档] → 明确基于当前两库实现实施；最终归档遵循依赖顺序，不能把本次当作知识库基础规格替代品。

## Migration Plan

1. 实现 v1/v2 读取、纯迁移、严格验证与 v2 备份，并以当前 v1 样本验证无数据损失。
2. 在相同写队列内接入计划生成／评分与恢复冲突处理，再接 UI；旧数据首次成功写入整体升级。
3. 运行离线和隔离浏览器测试、查看长内容与复习实际截图、更新 README、重打包并逐文件比对。
4. 发布前建议导出旧版备份。v2 不支持降级读写；回滚旧扩展须恢复升级前 v1 备份，会丢失升级后学习记录。不得静默降级覆盖 v2。
